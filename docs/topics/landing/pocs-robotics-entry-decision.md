## en
- **Rabbit: write the intent field, not just the spend cap.** A session-key mandate that only checks an amount limit repeats the reward-shaping trap this piece names — a cap constrains the amount, not the purchase — so add an explicit "what this transaction is for" field to the mandate schema before shipping more mandate types.
- **OFA: name the question before designing the auction.** Before wiring up an ATLAS-style solver, write one paragraph on which question it answers — best price, best fill probability, or best latency — the same forced choice the piece makes before any robotics purchase; the four entry points not being substitutes is the same warning for competing solver strategies.
- **Devnet: pick the reproducible tool over the fast one.** When choosing infrastructure for the hosted Anvil devnet, weight "others have already run this and can unblock me" over a raw speed claim, the same call the piece makes for MuJoCo over Genesis.

## ko
- **Rabbit: 지출 한도가 아니라 의도 필드를 적는다.** 금액 한도만 확인하는 세션 키 매니데이트는 이 글이 말하는 리워드 셰이핑 함정을 그대로 반복한다 — 한도는 금액을 제한할 뿐 구매 자체를 제한하지 않는다 — 그러니 매니데이트 종류를 더 추가하기 전에 "이 트랜잭션이 무엇을 위한 것인지"를 명시하는 필드를 스키마에 넣는다.
- **OFA: 경매를 설계하기 전에 답할 질문부터 정한다.** ATLAS 스타일 솔버를 연결하기 전에, 그것이 답하는 질문이 최적 가격인지 체결 확률인지 지연시간인지 한 문단으로 적는다. 이 글이 로봇 구매 전에 강제하는 선택과 같으며, 네 가지 진입 경로가 서로 대체재가 아니라는 경고는 경쟁하는 솔버 전략에도 그대로 적용된다.
- **Devnet: 빠른 도구보다 재현 가능한 도구를 고른다.** 호스팅된 Anvil devnet의 인프라를 고를 때는 순수 속도 주장보다 "이미 남들이 돌려봤고 막히면 물어볼 수 있다"는 쪽에 가중치를 둔다. 이 글이 Genesis 대신 MuJoCo를 고르는 것과 같은 판단이다.
