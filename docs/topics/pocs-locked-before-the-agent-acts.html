The budget is locked before the agent acts, and released only if the result verifies

Four Pillars walks through Talus v2, which folds an AI agent's permissions, budget, verification and schedule into one onchain execution model. Heavy computation stays off-chain; what goes on-chain is who was allowed to call what, what it cost, what evidence came back and whether that evidence was accepted. It is the most complete version of a move that has appeared three times this week — enforcement migrating from catching a violation afterwards to making it impossible — and it is also the clearest case of what that move still cannot do.

Brief &middot; v2.0.0 mainnet, spec described as actively developing. For Jayverse: the per-occurrence authority scoping is directly reusable; the verification boundary is the thing to argue with.

English한국어
English한국어

Why

A wrong answer from a chatbot is free to discard. Once an agent calls a paid API, moves an asset, or delegates to another agent, a small error costs money the moment it happens. So the interesting question is not how to make agents smarter but how to make delegation survivable: who acted, under whose authority, at what cost, and what happens when the result is wrong.

Talus's answer is to fix authority and money before execution. Costs are locked per vertex and paid only after the result passes verification; a price snapshot holds even if the tool changes its price mid-run; unused budget is refunded and a failure settles only the costs already incurred. Money cannot move for work that did not happen.

How it works

Authority is scoped per occurrence, not per agent

This is the part worth stealing outright.

An agent capability declares its fixed tools by registry identifier, checked against the tool registry at registration time. Then at execution a permission object binds the capability identifier, interface revision, graph and current vertex together — so an approval covers one execution, or one specific scheduled task. Even when an agent holds several capabilities, only the permitted tool set for that execution applies. Recurring tasks do not carry broad standing authority: an approval tied to a task identifier is copied into the execution object created for each occurrence.

Compare that with how delegation usually goes wrong. An API key is authority with no expiry and no scope. An unlimited token allowance is authority sized to your whole balance. A session key, as in the ERC-4337 item, is better — bounded by amount and time — but still one grant covering many future actions. Talus narrows the grant to the single run, and re-derives it each time. The blast radius of a compromised agent is one occurrence's budget.

Three verification paths, and what none of them checks

PathWhat it establishes
Basicthe result was recorded as submitted
Signedintegrity — these outputs were computed by the registered tool from the legitimate inputs
External Move contractthe output satisfies predefined conditions against on-chain state, including a zk proof against an on-chain commitment

Each vertex in the same graph can sit at a different level, which is the right granularity: a price lookup and an order submission do not deserve the same scrutiny. The verifier returns an acceptance or rejection plus a hash summarising the reason, and the verdict controls settlement — rejected or expired means the failure is processed and the unused budget refunded. Both the decision and the settlement are Sui transactions, so a third party with a transaction hash and execution identifier can reconstruct which result came from which vertex.

Now the boundary, which the article does not draw. All three paths verify provenance and policy. None verifies judgment. A signed result proves the registered tool produced it from legitimate inputs; it does not make the answer right. The external path can enforce a policy — this action satisfies a stated constraint — but the constraint has to be expressible in a Move contract, and the interesting failures of agents are not constraint violations. They are plausible, well-formed, in-budget, correctly-signed wrong answers.

That is Eng #399's slop grenade in infrastructure form. Talus makes it impossible for an agent to spend more than you allowed or to call a tool you did not permit, and it makes every step auditable afterwards. It does not make the agent right, and a system that settles confidently on verified-but-wrong output has moved the failure rather than removed it — which is the same sentence this week's other items keep producing.

The measure the article proposes for itself

Worth quoting because it is unusually self-disciplining: as the cost of creating an agent falls, the number of registered agents is a weak measure. The relevant measures are how often the same Task produces paid calls, verification decisions and settlement across multiple Occurrences; per-vertex success and refund rates; the share of executions through external verification contracts; and the number and deposit distribution of independent Leaders.

A protocol that names the metric on which it can be judged to have failed is making a falsifiable claim. Most do not.

What is not yet proven

The Talus/acc cohort ran on v1 — 50+ applicants, seven to Demo Day, winners SuperStake, Agama and Noodles Finance. So the demonstrations predate the permission and budget system this item is about; the first v2 migrations are described as underway. Leaders must now register and stake $US and can be slashed, with a primary and backup assigned per request, which is a real liveness answer, but the $US convergence — Leader deposits, tool bonds and priority fees in one token — is also the point where the execution record and the token economy become the same object, and that is a design decision with consequences not yet observable.

Where it lands in Jayverse

Per-occurrence authority, applied to the Auditor. Today's authority matrix asks who may act. Add the Talus shape: an approval that is derived per run and carries its own budget, so the matrix becomes who may act, for how much, this once. Then add the row the article does not have — what class of error this catches, and what class it settles confidently. That second column is where the spend-control ledger, the abstraction-liability matrix and this converge.

English한국어

에이전트가 움직이기 전에 예산이 잠기고, 결과가 검증되어야 풀린다

Four Pillars가 Talus v2를 짚는다. AI 에이전트의 권한, 예산, 검증, 스케줄을 하나의 온체인 실행 모델로 접는다. 무거운 연산은 오프체인에 남고, 온체인에 올라가는 것은 누가 무엇을 호출할 수 있었는가, 얼마가 들었는가, 어떤 증거가 돌아왔는가, 그 증거가 받아들여졌는가다. 이번 주에 세 번 나온 그 수 — 위반을 나중에 잡는 대신 애초에 불가능하게 만들기 — 의 가장 완성된 판본이고, 동시에 그 수가 여전히 할 수 없는 일을 가장 선명하게 보여 주는 사례다.

Brief &middot; v2.0.0 메인넷이고 명세는 계속 개발 중이라고 밝힌다. Jayverse에서는 occurrence 단위 권한 범위가 바로 재사용 가능하고, 검증의 경계가 논쟁할 지점이다.

왜

챗봇의 틀린 답은 버리면 그만이다. 에이전트가 유료 API를 호출하거나 자산을 옮기거나 다른 에이전트에 위임하는 순간, 작은 오류가 발생하는 그 시점에 돈이 된다. 그러니 흥미로운 질문은 에이전트를 어떻게 똑똑하게 만드느냐가 아니라 위임을 어떻게 견딜 만하게 만드느냐다. 누가 행위했는가, 누구의 권한으로, 얼마를 들여, 그리고 결과가 틀렸을 때 어떻게 되는가.

Talus의 답은 권한과 돈을 실행 전에 고정하는 것이다. 비용은 vertex 단위로 잠기고 결과가 검증을 통과한 뒤에만 지급된다. 실행 도중 도구가 가격을 바꿔도 스냅샷 가격이 유지된다. 쓰지 않은 예산은 환불되고, 실패는 이미 발생한 비용만 정산한다. 일어나지 않은 작업에 대해 돈이 움직일 수 없다.

동작 방식

권한은 에이전트가 아니라 occurrence 단위로 범위가 잡힌다

그대로 훔칠 만한 부분이다.

에이전트 capability는 자기가 쓸 도구를 레지스트리 식별자로 선언하고, 등록 시점에 도구 레지스트리와 대조된다. 그리고 실행 시점에 permission object가 capability 식별자, 인터페이스 리비전, 그래프, 현재 vertex를 하나로 묶는다. 그래서 승인은 단일 실행, 또는 특정 예약 작업 하나만 덮는다. 에이전트가 여러 capability를 들고 있어도 그 실행에 허용된 도구 집합만 적용된다. 반복 작업이 넓은 상시 권한을 들고 다니지 않는다. 작업 식별자에 묶인 승인이 occurrence마다 생성되는 실행 객체로 복사된다.

위임이 보통 어떻게 망가지는지와 비교해 보자. API 키는 만료도 범위도 없는 권한이다. 무제한 토큰 허용량은 잔액 전체 크기의 권한이다. ERC-4337 항목의 세션키는 낫다. 금액과 시간으로 묶여 있으니까. 그래도 여러 미래 행위를 덮는 하나의 부여다. Talus는 부여를 단일 실행으로 좁히고 매번 다시 파생시킨다. 탈취된 에이전트의 폭발 반경이 occurrence 하나의 예산이다.

세 가지 검증 경로, 그리고 어느 것도 확인하지 않는 것

경로무엇을 확립하나
기본제출된 대로 결과가 기록되었다
서명무결성 — 이 출력이 등록된 도구에 의해 정당한 입력으로부터 계산되었다
외부 Move 컨트랙트출력이 온체인 상태에 대해 사전 정의된 조건을 만족한다. 온체인 커밋먼트에 대한 zk 증명 포함

같은 그래프의 vertex마다 다른 수준을 쓸 수 있고, 그것이 옳은 입도다. 시세 조회와 주문 제출이 같은 강도의 검증을 받을 이유가 없다. 검증자는 수락/거절과 그 이유를 요약하는 해시를 돌려주고, 판정이 정산을 통제한다. 거절되거나 만료되면 실패로 처리되고 쓰지 않은 예산이 환불된다. 판정과 정산 모두 Sui 트랜잭션이라, 트랜잭션 해시와 실행 식별자를 가진 제3자가 어떤 결과가 어느 vertex에서 나왔는지 재구성할 수 있다.

이제 글이 긋지 않은 경계다. 세 경로 모두 출처와 정책을 검증한다. 어느 것도 판단을 검증하지 않는다. 서명된 결과는 등록된 도구가 정당한 입력으로 그것을 만들었음을 증명할 뿐, 답이 맞다고 만들어 주지 않는다. 외부 경로는 정책을 강제할 수 있다. *이 행위가 명시된 제약을 만족한다*고. 그러나 그 제약이 Move 컨트랙트로 표현 가능해야 하고, 에이전트의 흥미로운 실패는 제약 위반이 아니다. 그럴듯하고, 형식이 멀쩡하고, 예산 안에 있고, 올바르게 서명된 틀린 답이다.

Eng #399의 slop grenade가 인프라 형태로 나타난 것이다. Talus는 에이전트가 허용한 것보다 더 쓰거나 허락하지 않은 도구를 부르는 일을 불가능하게 만들고, 모든 단계를 사후 감사 가능하게 만든다. 에이전트를 맞게 만들어 주지는 않는다. 그리고 검증은 되었지만 틀린 출력 위에 자신 있게 정산하는 시스템은 실패를 제거한 것이 아니라 옮긴 것이다. 이번 주 다른 항목들이 계속 만들어 내는 바로 그 문장이다.

글이 스스로에게 제시하는 척도

인용할 만하다. 자기 규율이 드문 방식이라서다. 에이전트를 만드는 비용이 떨어질수록 등록된 에이전트 수는 약한 척도가 된다. 의미 있는 척도는 같은 Task가 여러 Occurrence에 걸쳐 유료 호출과 검증 판정과 정산을 얼마나 자주 만들어 내는가, vertex별 성공률과 환불률, 외부 검증 컨트랙트를 거친 실행의 비중, 독립 Leader의 수와 예치금 분포다.

자신이 실패했다고 판정될 척도를 직접 대는 프로토콜은 반증 가능한 주장을 하는 것이다. 대부분은 하지 않는다.

아직 증명되지 않은 것

Talus/acc 코호트는 v1에서 돌았다. 50개 이상 지원, 7팀 데모데이, 우승은 SuperStake·Agama·Noodles Finance. 즉 시연은 이 항목이 다루는 권한·예산 체계보다 앞선다. v2로의 첫 이전은 진행 중이라고만 적혀 있다. Leader는 이제 등록하고 $US를 스테이킹해야 하며 슬래싱 대상이고 요청마다 주·예비 Leader가 배정되는데, 이는 진짜 가용성 대책이다. 다만 $US로의 수렴 — Leader 예치금, 도구 본드, 우선순위 수수료가 한 토큰으로 — 은 실행 기록과 토큰 경제가 같은 객체가 되는 지점이기도 하고, 그 결과는 아직 관측할 수 없다.

Jayverse에서의 위치

occurrence 단위 권한을 Auditor에 적용한다. 지금의 권한 매트릭스는 누가 행위할 수 있는가를 묻는다. Talus의 모양을 더한다. 실행마다 파생되고 자기 예산을 들고 있는 승인. 그러면 매트릭스가 누가, 얼마까지, 이번 한 번 이 된다. 그다음 글에 없는 행을 더한다. 이 설계가 잡아내는 오류의 종류와, 자신 있게 정산해 버리는 오류의 종류. 그 두 번째 열에서 지출 통제 원장, 추상화 책임 매트릭스, 그리고 이것이 수렴한다.
