Mechanism (the article's description)

  • DAG workflow engine on Sui. A task is split into vertices; each vertex is a tool implemented as an offchain HTTP service or an onchain Move module. Execution ends in one of several mutually exclusive output variants, which determine the next branch. An execution path is a Walk and can split, run in parallel, or repeat.
  • v2 builds on v1's tool registry, bond deposits, Signed HTTP and scheduled execution, and binds caller, permitted tools, funding source and verification method to each vertex.
  • Agent = onchain actor with one or more skills; the agent registry tracks active status, linked graph, required tools, interface revision, scheduled-task count.
  • Permissions: capability declares fixed tools by registry id, checked at registration; at execution a permission object binds capability id + interface revision + graph + current vertex ⇒ approval limited to one execution or one scheduled task; approval tied to a task id is copied into the execution object per occurrence.
  • Budget: locked per vertex, paid after the result is finalized. Each tool has a cashier with a mandatory fixed SUI price (zero = public), plus optional finite credits and time passes. Snapshot price survives mid-run price changes. Unused budget refunded; failure settles only costs incurred.
  • Scheduling: Task → Schedule → Occurrence. Reserve stores per-occurrence history to prevent double allocation; a Task can attach a priority fee in $US for Leader dispatch precedence.
  • Leader: coordinator; subscribes to onchain events, calls tools, submits results. Must register and stake $US, slashable; primary and backup assigned per request.
  • Three verification paths: basic recording; signed (registered signing key proves the registered tool computed the outputs from legitimate inputs); external Move contract (conditions against onchain state, including a zk proof against an onchain commitment). Verifier returns accept/reject plus a reason hash. The verdict controls settlement. Decision and settlement are Sui transactions.
  • Protocol state versioned at every root object; each execution pins the immutable package config captured at creation, so the protocol can upgrade without breaking live agents.

The article's own proposed metrics

  • Registered agents = weak measure. Instead: how often the same Task produces paid calls, verification decisions and settlement across multiple Occurrences; per-vertex success and refund rates; share of executions through external verification contracts; number and deposit distribution of independent Leaders; how long recurring occurrences continue; whether operators keep replenishing reserves.
